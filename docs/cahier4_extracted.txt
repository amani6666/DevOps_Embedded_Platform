1. Note d'orientation
Cette version enrichit le projet initial : l'écosystème Arduino est remplacé par Zephyr
RTOS pour le microcontrôleur, et la passerelle (Raspberry Pi) utilise une image Linux sur-
mesure construite avec Yocto Project. Ces deux ajouts sont des compétences très
valorisées en entreprise, mais nettement plus difficiles qu'Arduino/Docker seul.
A Principe directeur accepté par l'équipe : l'apprentissage prime sur la perfection.
On accepte la difficulté, mais on sécurise la démo finale avec un plan de secours (section
8).
1bis. Positionnement "Industrie 4.0" (sans changement de stack)
Une troisième proposition, orientée "maintenance prédictive industrielle" (STM32, bus
CAN, capteurs industriels, PostgreSQL, Prometheus, Kubernetes), a été étudiée. Décision
de l'équipe : ne pas l'intégrer techniquement, pour les raisons suivantes :

e Le matériel proposé (STM32, transceiver CAN, capteurs industriels) n'est pas
disponible et remettrait en cause tout le travail déjà engagé sur ESP32.

« Les briques ajoutées (PostgreSQL, Prometheus, Kubernetes) font doublon avec
l'infrastructure déjà choisie (InfluxDB, Grafana) sans apporter de valeur pédagogique
supplémentaire.

«  Lenombre d'options laissées ouvertes (3 frameworks frontend, 5 frameworks IA) n'est
pas un plan de travail exploitable en 7 semaines.

Ce qui est retenu de cette proposition, sans coût technique supplémentaire :

e Le positionnement narratif du projet dans le rapport final : la plateforme est
présentée comme une démonstration (proof of concept) de maintenance prédictive
industrielle, le capteur DHT22/ESP32 jouant le rôle d'un capteur industriel générique.

«  Leraisonnement multi-étapes de l'Agent 4 (détection d'anomalie > recherche
documentaire > récupération des limites > comparaison > diagnostic >
recommandation > notification), qui remplace le simple mode "question/réponse" —
voir le guide détaillé de Sahar.

6. Méthode de travail (rappel)

Chaque tâche part d'une branche Git dédiée, revue par Pull Request avant fusion. Point
d'intégration hebdomadaire le vendredi : on remplace progressivement les mocks par les
vrais composants. Test d'intégration global via (docker-compose up). (Voir le Guide
d'Intégration Équipe existant — la mécanique ne change pas, seuls les contrats JSON ci-
dessus sont mis à jour.)
